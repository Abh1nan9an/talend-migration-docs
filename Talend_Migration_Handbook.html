“Local tests” means the Groovy scripts, executed inside the iFlow design by a local simulator, produce exactly the calls of an executable Python specification of the Talend job. Parity with production Talend needs the client's archived data (see Validation).

Approach

The method is: analyse the source exactly, keep an executable reference, prove parity against real archived data, then port and package.

  1. Export job documentation from Talend Studio

    “Generate Doc as HTML” per job gives every component parameter (SOQL, endpoints, Java code), schemas, connections, context values per environment and every tMap / tXMLMap expression. It is the complete specification of what the job does.

  2. Parse the export into structured data

    talend_doc_parser.py turns each job into JSON; build_inventory.py classifies all 50 packages by pattern, map size, custom Java and shared sub-jobs.

  3. List what the export does not contain

    Project routines, tWriteXMLField trees, XML namespace URIs and loop elements, TMC schedules and per-task context values. Request exactly these from the client.

  4. Write a Python reference with Java semantics

    A tMap expression is Java. The reference reproduces its behaviour, including nulls, string identity and number formatting, and flags where that behaviour is clearly unintended.

  5. Choose the parity oracle

    Archived evidence of what Talend really produced: Talend_Jobmonitor__c payloads in Salesforce, TMC logs of tLogRow, archived files.

  6. Port to Groovy and design the iFlow as data

    One Groovy function per iFlow script step, with the same names as the reference. The iFlow is described once in flow.py, then rendered to BPMN and executed by the local simulator.

  7. Build, deploy, verify live

    Bundles are generated from adapter and step property sets harvested from real tenant iFlows, validated, uploaded and deployed through the Content API, then the oracle inputs are replayed against the deployed iFlow.

Java semantics to keep

Talend expressions run as Java, and production data depends on that behaviour. The reference implementation (common/reference/talend_rt.py) and the Groovy scripts reproduce each case below. Where the behaviour looks unintended, it is kept by default and raised as a decision.

PI_SF_Wholesaler

SAP customer master arrives from PI as customer* XML files. For each customer the job looks up the Account record type and owner, upserts the Account on ID2__c, aligns BrandDetail__c owners with the Account owner, writes a run record to Talend_Jobmonitor__c and archives the file.

Talend structure

  • tFileList → tRunJob per file
  • tFileInputXML → tXMLMap_1 (loop customer)
  • tMap_2 + RELOAD lookups RecordType, User
  • tSalesforceOutput_1 UPSERT Account
  • tMap_3 + RELOAD lookup BrandDetail__c → UPDATE
  • tFileCopy OK / FAILED · talend_jobmonitor

iFlow Talend_PI_SF_Wholesaler

  • SFTP sender → Read configuration → initRun
  • Router → Looping Process Call “Process one customer”
  • RecordType query → Router (owner given?) → User query
  • buildAccountUpsert → PATCH Account
  • BrandDetail query → Router → PATCH collection
  • finishRun → monitor → SFTP Archive · Exception Subprocess → SFTP Failed

The full 29-field mapping is in interfaces/PI_SF_Wholesaler/SPEC.md.

Deliberate deviations

  • Customers without an owner: Talend's LIKE '%' lookup assigns an arbitrary user. The iFlow skips OwnerId; parameter Owner_Policy=talend restores the original.
  • Per-customer upserts instead of batches of 200: a failing file keeps the customers already written (upserts are idempotent, so reprocessing is safe).
  • Unreadable files are also logged to Talend_Jobmonitor__c (code 999); Talend skipped them.

SF_PI_PaymentDetail

For Service orders that are invoiced but not complete, the interface asks SAP for invoice and payment details through PI, then completes or keeps the order open, updates contract accounting for mandatory-paid types, and writes every SAP answer to a feedback file.

Talend structure

  • Master: tSalesforceInput SOQL → tMap_1 string → tRunJob per order
  • tExtractDelimitedFields → tXMLMap_1 SOAP request
  • tSOAP_1 → tFilterRow (no fault) → tXMLMap_2 → tAggregateRow
  • tMap_1 / tMap_2 rules → UPDATE SCOrder__c
  • tMap_3 + RELOAD accounting → UPDATE SCContractAccounting__c
  • tFileOutputDelimited feedback file

iFlow Talend_SF_PI_PaymentDetail

  • Timer → Read configuration → paged order query (looping)
  • Looping Process Call “Process one order” with Exception Subprocess
  • nextOrder → POST to PI → evaluatePaymentResponse
  • Router → PATCH order → Router → accounting query → Router → PATCH collection
  • buildFeedbackFiles → Router → Splitter → SFTP

Business rules

OrderIsArchiv    = (FULLY_PAID ≈ "A" and invoice) or (invoice and VALUE == 0)
OrderIsPaid      = FULLY_PAID ≈ "X" or CLEARING_DATE is a valid date (not 0000-00-00)
mandatorypaid    = Type__c in {5711, 5712, 5730, 5732, 5734}
OrderIsCompleted = (mandatorypaid and OrderIsPaid) or (not mandatorypaid and OrderIsArchiv)
                   or PriceNet__c == 0

completed → Status__c 5508, InvoicingStatus__c 52404, accounting "booked"
otherwise → Status__c 5506, InvoicingStatus__c 52403, accounting "invoiced"

Deliberate deviations

  • ERP order number back-fill (update_erporderno) is not implemented: its filter can never pass in Talend, and if it did it would throw. Business to confirm.
  • Several invoices for one order: one update with the last row's values (Talend sent duplicate IDs in one batch).
  • Feedback file: one file per country per run instead of appending to a daily file.
  • Orders are all-or-nothing; a failure isolates that order only.

Export traps

Each of these would have produced a migration that looked correct and was wrong. They apply to every future job taken from the same export.

Standalone tMap_N.xml files are not per job. Talend writes all jobs of a package into shared file names, so the last job exported wins: the master's tMap_1.xml actually contained the child's map. The per-job HTML is authoritative. The parser only trusts a side XML when its tables and expressions match the HTML: 338 of 515 mappers verified, 177 taken from HTML only.

The HTML omits lookup behaviour. lookup-mode="RELOAD" and globalMapKeysValues, which define per-row lookup queries, exist only in the verified side XML.

Java code has literal newlines inside XML attributes. A normal XML parser folds them into spaces, so every // comment swallows the rest of the code. The parser escapes them before parsing.

Not in the documentation export: project routine source, tWriteXMLField “Configure XML Tree”, namespace URIs and loop elements of tXMLMap trees, TMC schedules and per-task context values.

Ask for the Talend project export as well. The client sent build exports of all 50 packages on 14 Oct 2026 (job .item files, generated Java, routine source, per-environment contexts). It closed every gap above except the scheduler, and it changed three things we had believed:

  • StringMod.PadLeft throws on null instead of returning null — a defect in an interface we had already deployed. Fixed and redeployed.
  • The SOAP request envelope uses the SOAP 1.1 namespace although the call is SOAP 1.2. Also fixed and redeployed.
  • A project routine opens its own MySQL connection (TDIData → talend_tdi.datamap) in 13 packages, with the credentials hardcoded in the routine source. No component inventory can show this; it is a 14th end system and a security item.

Lesson for the next estate: the documentation export tells you what a job looks like, the project export tells you what it does.
